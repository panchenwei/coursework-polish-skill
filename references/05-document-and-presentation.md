# 文档版式、PPT与演示

## 0. 先产生可用成品

当任务目标是制作DOCX、PPTX或视频时，第一里程碑必须是一个完整可打开的版本，而不是越来越长的评审规则。推荐循环：

```text
完整初稿 → 必需内容检查 → 数据一致性 → 版式/时长检查 → 定向修改 → 冻结
```

若连续审查没有产生新成品、没有提高官方评分点或只增加自设要求，应停止扩展审计并回到交付。高标准用于提高成品，不得阻止成品出现。

## 1. 锁定格式合同

从任务书提取：文件格式、字体和字号、行距、页边距、页数计算、分栏、封面/目录/附录/代码是否计页、命名规则、图片/表格/引用格式。

没有明确允许的非常规排版不能因为“节省空间”就视为安全。必要时询问教师并保存答复。

## 2. 超页处理顺序

1. 删除重复背景；
2. 删除重复算法定义；
3. 让一个实验支持多个相关问题；
4. 把枚举文字改成紧凑表格；
5. 合并重复图；
6. 正文只保留最强证据；
7. 补充证据移附录并交叉引用；
8. 缩短重复 caption；
9. 修复不必要分页和 section break；
10. 重新渲染检查。

不得删 required answer、关键证据、理论推导、限制或结论来换页数。

## 3. Word/DOCX验证

生成成功不等于版式正确。每次重要修改后：

- 用目标编辑器或可靠渲染器打开；
- 检查所有页面或至少所有改动页和章节边界；
- 检查表图裁切、重叠、caption分离、空白页、字体替换和低分辨率；
- 检查页码、目录和交叉引用；
- 用实际分页判断页数，而不是字数估算；
- 关闭文档时避免无意更新字段或改写格式。

新章节不应默认空出整页；表图之后若能继续正文，不要留下大块留白。

## 4. PPT结构

PPT必须同时包含：official required output、explanatory evidence、application/design、reflection和final decision。

高密度结果页宁可朴素清晰，也不要缩成不可读小字。图太密时，从正式 raw data 制作 PPT-friendly 派生图，并验证数值与报告一致。

每张图 caption 说明它证明什么。不要只放文件名或“Figure shows results”。

## 5. 报告—PPT—讲稿一致性

建立矩阵：

| Slide | Required point | Report source | Evidence source | Spoken conclusion | Owner/time |
|---|---|---|---|---|---|

先冻结 PPT，再按最终 slide order 写讲稿。不要先写讲稿再强行适配不断变化的幻灯片。

讲稿应自然解释，不能逐字读报告。所有数字、路径、类名和结论必须与报告一致。

冻结后记录唯一正式版本和哈希。视频录制使用的PPT、最终上传PPT和讲稿引用的页序必须一致；发生修改时，要明确旧版本失效，避免多个“final”并存。

## 6. 演示与视频

- 先确认时长、格式、出镜、声音和语言要求；
- 分配每页时间并留缓冲；
- 成员内容与真实工作和确认信息一致；
- GUI用于解释过程，不替代正式证据；
- 展示流程应清楚；
- 视频使用的 PPT 必须与上传版本一致；
- 录制后检查容器、音视频流、总时长和代表性片段。

专业剪辑、复杂动效或电影级画面属于内部质量目标，除非任务书明确要求，否则不得成为官方评分扣分项。先保证内容覆盖、声音、出镜、时长、语言和文件格式等硬要求，再投入可选制作。

## 7. 视觉质量底线

- 轴、单位和图例可读；
- 颜色不仅靠色相区分，兼顾对比度和可访问性；
- 不使用装饰性3D图；
- 不把长代码整页贴进PPT；
- UML只保留关键关系；
- 截图裁剪到有效区域并配说明；
- 封面、标题、姓名和组号遵循任务要求，不让非重点信息抢占视觉中心。

## 8. 官方未规定格式时的 LaTeX 决策

格式优先级：教师模板 → 教师格式 → 课程/学校格式 → 用户现有正式格式 → 内部推荐。

只有在官方完全未规定、且报告属于计算机、工程、算法、实验或研究型技术报告时，才向用户推荐本地 LaTeX 环境和 `IEEEtran` 双栏。让用户明确选择：IEEE 双栏、常规单栏或保持现有格式。不得静默转换现有文档；非技术论文不机械套用 IEEE；缺少工具链时先报告并询问是否配置。

用户确认 LaTeX 后：

- `main.tex` 作为唯一正式入口；
- 按真实章节拆分 `sections/`，不照搬与 rubric 无关的论文结构；
- 图、表和 `references.bib` 使用稳定相对路径；
- 使用本地编辑器/工具链完整编译；
- 检查错误、未定义引用、overfull/underfull、字体、页数和双栏溢出；
- 实际渲染最终 PDF，逐页检查跨栏图、表格、caption和可读字号。

## 9. 数据图与论文结构图

数据图回答数值问题，必须从正式 raw data 生成。论文结构图回答系统、流程、机制、状态或组件关系问题。先定义图要证明的单一要点，再选图形。

所有正式图表使用论文发表级标准：

- 优先交付 SVG/PDF 等矢量格式；必须使用位图时，在最终印刷尺寸下至少 300 ppi（截图类按内容可接受 150 ppi，但文字必须清晰）；
- 在报告最终单栏/双栏宽度下检查字体、线宽、标记和图例，不靠放大才能阅读；
- 统一字体、字号层级、线宽、配色和类别编码；
- 轴、单位、统计量、样本量、误差含义和图例完整；
- 配色兼顾灰度和色觉可访问性，不使用彩虹色、装饰性3D、阴影或无数据意义的视觉效果；
- 数据图保留生成脚本、raw source、筛选/变换和统计口径；
- 架构图的组件、流程和强调必须与正文、代码和 caption 一致；
- caption 直接说明图支持的结论和必要限制，而不是只写图名；
- 在最终 DOCX/PDF/PPT 中实际渲染并检查裁切、重叠、留白和可读性。

教师模板、目标会议/期刊或课程图形规范高于内部默认。

架构图、流程图、机制图、状态机、模型结构、before/after和组件交互优先考虑 `$figgenie-paper-diagram`；它不用于折线图、条形图、箱线图、散点图或热力图。

当结构图能明显帮助评分者理解时，提醒用户：

> 当前内容适合制作专业架构图或流程图，建议使用 `$figgenie-paper-diagram`。是否使用？

- skill 可用：按其规范执行；
- skill 不可用：说明用途，让用户选择安装/配置或其他矢量方案；
- 用户拒绝或图无论证价值：不强行制作。

使用 FigGenie 时必须完成：

```text
检索相关论文图 → 分析布局/论证/视觉编码 → intake → brief → 用户确认
→ spec → exemplar/layout → drawing plan
→ SVG → lint/render/look-and-fix → SVG/PDF/PNG/caption → 用户复核
```

论文图用于研究同领域如何安排信息、证明机制和选择视觉编码。优先选择高度相关、同行评审且具领域权威性的论文：期刊核验当前影响因子/JCR分区，计算机顶会核验CCF、CORE或领域公认等级。每个视觉参考记录论文、年份、venue、权威依据及年份、figure编号和具体借鉴点。不得为会议虚构影响因子，也不得直接复制论文图、图标、独特构图或受版权保护素材。最终图必须基于当前项目自己的组件、数据、术语和论证重新设计。

IEEE 双栏报告中，单栏图按单栏打印宽度设计，总览图仅在必要时跨双栏。最终交付使用可复现的 SVG/PDF，正文 caption 说明图证明什么。

## 10. 图表与实践闭环

图表规划发生在实验设计阶段，以确定需要采集的指标。生成后必须回到实践数据核对：单位、样本、变换、统计口径、异常值和结论。若图暴露新的异常、不可读关系或缺失变量，回到实验或设计阶段处理，不能只修饰图面。

FigGenie 的安装、检测和联合部署见 [11-figgenie-integration.md](11-figgenie-integration.md)。
