# 文档版式、PPT与演示

## 0. 先产生可用成品

当任务目标是制作DOCX、PPTX或视频时，第一里程碑必须是一个完整可打开的版本，而不是越来越长的评审规则。推荐循环：

```text
完整初稿 → 必需内容检查 → 数据一致性 → 版式/时长检查 → 定向修改 → 冻结
```

若连续审查没有产生新成品、没有提高官方评分点或只增加自设要求，应停止扩展审计并回到交付。高标准用于提高成品，不得阻止成品出现。

## 1. 锁定格式合同

从任务书提取：文件格式、字体和字号、行距、页边距、页数计算、分栏、封面/目录/附录/代码是否计页、命名规则、图片/表格/引用格式。

没有明确允许的非常规排版不能因为“节省空间”就视为安全。必要时询问教师并保存答复。

## 2. 超页处理顺序

1. 删除重复背景；
2. 删除重复算法定义；
3. 让一个实验支持多个相关问题；
4. 把枚举文字改成紧凑表格；
5. 合并重复图；
6. 正文只保留最强证据；
7. 补充证据移附录并交叉引用；
8. 缩短重复 caption；
9. 修复不必要分页和 section break；
10. 重新渲染检查。

不得删 required answer、关键证据、理论推导、限制或结论来换页数。

## 3. Word/DOCX验证

生成成功不等于版式正确。每次重要修改后：

- 用目标编辑器或可靠渲染器打开；
- 检查所有页面或至少所有改动页和章节边界；
- 检查表图裁切、重叠、caption分离、空白页、字体替换和低分辨率；
- 检查页码、目录和交叉引用；
- 用实际分页判断页数，而不是字数估算；
- 关闭文档时避免无意更新字段或改写格式。

新章节不应默认空出整页；表图之后若能继续正文，不要留下大块留白。

## 4. PPT结构

PPT必须同时包含：official required output、explanatory evidence、application/design、reflection和final decision。

高密度结果页宁可朴素清晰，也不要缩成不可读小字。图太密时，从正式 raw data 制作 PPT-friendly 派生图，并验证数值与报告一致。

每张图 caption 说明它证明什么。不要只放文件名或“Figure shows results”。

## 5. 报告—PPT—讲稿一致性

建立矩阵：

| Slide | Required point | Report source | Evidence source | Spoken conclusion | Owner/time |
|---|---|---|---|---|---|

先冻结 PPT，再按最终 slide order 写讲稿。不要先写讲稿再强行适配不断变化的幻灯片。

讲稿应自然解释，不能逐字读报告。所有数字、路径、类名和结论必须与报告一致。

冻结后记录唯一正式版本和哈希。视频录制使用的PPT、最终上传PPT和讲稿引用的页序必须一致；发生修改时，要明确旧版本失效，避免多个“final”并存。

## 6. 演示与视频

- 先确认时长、格式、出镜、声音和语言要求；
- 分配每页时间并留缓冲；
- 成员内容与真实工作和确认信息一致；
- GUI用于解释过程，不替代正式证据；
- 展示流程应清楚；
- 视频使用的 PPT 必须与上传版本一致；
- 录制后检查容器、音视频流、总时长和代表性片段。

专业剪辑、复杂动效或电影级画面属于内部质量目标，除非任务书明确要求，否则不得成为官方评分扣分项。先保证内容覆盖、声音、出镜、时长、语言和文件格式等硬要求，再投入可选制作。

## 7. 视觉质量底线

- 轴、单位和图例可读；
- 颜色不仅靠色相区分，兼顾对比度和可访问性；
- 不使用装饰性3D图；
- 不把长代码整页贴进PPT；
- UML只保留关键关系；
- 截图裁剪到有效区域并配说明；
- 封面、标题、姓名和组号遵循任务要求，不让非重点信息抢占视觉中心。
