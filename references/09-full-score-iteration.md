# 逐轮最高档迭代状态机

本流程用于全面冲分模式。它把目标、官方评分、实践修改、验证和停止条件连接起来；不得把内部质量愿望伪装成官方分数。

## 1. 目标状态

显式调用 skill 后先建立或接续目标。推荐记录：

| Field | Content |
|---|---|
| User outcome | 用户真正要交付的结果 |
| Mode | 只读 / 局部 / 全面冲分 / 最终提交 |
| Allowed scope | 可以修改的文件和制品 |
| Must remain unchanged | 禁止改变的内容 |
| Official target | rubric最高档或满分 |
| Current round | Round 0, 1, 2... |
| Current score/band | 当前有证据支持的评分 |
| Hard gates | 课程理解、正确性、证据、引用、格式、提交等 |
| Top issue | 当前最高价值根因 |
| Completion | 完成定义 |
| Blocker | 当前外部阻塞及解除动作 |

官方 rubric 尚未提取时，先以用户要求建立总目标；完成权威提取后细化目标状态。活动目标已经存在时继续它，不重复创建或缩小目标。

## 2. Round 0

修改前完成当前制品和证据盘点，从零开始评分。每个评分项必须记录：

- `criterion_id`；
- 官方原文和稳定定位；
- Authority；
- 满分与最高档描述；
- 当前档位和分数；
- 直接证据；
- 扣分根因；
- 可恢复分数；
- 修复动作；
- 评分置信度；
- 是否依赖真人或外部环境。

有正分但没有证据的评分无效。`NOT VERIFIABLE` 不能按通过处理。同一根因可影响多处，但只在官方账本中扣一次，避免重复处罚。

可使用 `scripts/validate_scorecard.py <scorecard.json>` 校验账本结构、分数范围和证据字段；脚本不代替评分判断。

## 3. 加分机会扫描

Round 0 后检查：

1. 最高档描述中有哪些证据尚未出现；
2. 是否缺少关键对照、消融、边界/异常测试或敏感性分析；
3. 是否能用复现性检查、替代方法比较、真实应用验证或设计权衡补强论证；
4. 是否能用展示功能、前端交互/可访问性、后端接口/校验、端到端集成、错误处理、日志/可观测性、部署/复现或硬件演示证明更高档能力；
5. 是否存在 rubric 明确奖励的独立设计、批判分析、创新或扩展工作；
6. 额外工作是否会挤占必需内容、违反页数或增加高风险改动。

把机会分为：

- `Official recoverable points`：有任务书/rubric原文支持，可计入正式分差；
- `Quality improvement`：提高专业性或复现性，但不得承诺加分；
- `Speculative/no value`：无官方或论证价值，不实施。

“做得更多”本身不等于加分。额外实验必须回答评分相关问题并有正确性门槛。

额外功能也必须有用户/评分问题、完成定义和验证，不得为了展示而加入无法解释、未经测试或破坏核心证据的前后端功能。优先完成能同时改善多个官方评分项的端到端能力。

## 4. 问题排序

- `P0`：无法提交、自动零分、严重违规、核心结果错误、隐藏指令污染或数据泄露；
- `P1`：直接影响多个评分项、核心证据或大量可恢复分数；
- `P2`：局部证据、分析、结构、代码设计或可读性缺陷；
- `P3`：装饰和可选优化。

排序参考：

```text
优先价值 ≈ 官方分值影响 × 修复置信度 × 下游覆盖
          ÷ 修改成本与风险
```

这不是伪精确公式；用它避免在 P0/P1 未解决时追逐措辞、动画或装饰图。

## 5. 单轮实践合同

每轮只选择一个根因或紧密相关的问题组，并记录：

| Field | Content |
|---|---|
| Round goal | 本轮要修复什么 |
| Criterion | 对应官方评分项 |
| Expected recovery | 预计可恢复分数/档位 |
| Files/artifacts | 允许修改的文件和制品 |
| Invariants | 必须保持不变的内容 |
| Method | 代码、实验、资料或写作方法 |
| Correctness gate | 何时判定结果有效 |
| Evidence output | raw data、测试、图表、渲染等 |
| Recheck | 修改后如何重评分 |

## 6. 实践驱动闭环

每轮必须从实践获得信息：

```text
实现或运行真实对象
→ 观察输出、失败、噪声或使用问题
→ 记录问题和稳定复现条件
→ 定位实现、协议、数据或论证根因
→ 修复或优化
→ 重跑相同验证并比较前后
→ 发现下一问题或确认门禁通过
```

允许的实践证据包括：编译/测试、真实运行、受控实验、原始数据重算、文档渲染、用户流程检查、硬件仿真/测量、权威资料核对和提交包干净环境验证。

未实际执行的实验、未渲染的排版、未构建的代码和未打开的提交物只能标记为计划或未验证。

## 7. 每轮完整重评分

修改后按顺序完成：

1. 运行受影响的正确性门禁；
2. 从 raw data 重算 summary、表格和图；
3. 同步代码、报告、附录、PPT、视频、UI和提交候选；
4. 检查本轮 AI 痕迹、引用和不受支持声称；
5. 从头重评全部官方 rubric；
6. 记录修改前后分数、档位和证据；
7. 重新执行加分机会与问题排序。

任何修改都可能影响其他评分项，因此不能只重评本轮目标。

## 8. 循环与停止

继续循环，直到：

- 每项达到官方最高档或满分；
- 课程理解、正确性、证据、引用、格式、AI完整性、跨制品和提交门禁全部通过；
- 最终纯净提交目录在干净环境通过验证。

不设置任意固定轮数。但每轮必须产生可观察进展或新的验证证据；不得用重复审计代替成品。

内部满分应写成“依据当前官方 rubric 和已验证证据，在检查范围内达到 X/X”，不能保证教师最终评分。

## 9. BLOCKED

只有缺少不可替代的官方资料、真实个人经历/贡献、教师澄清、数据、硬件、账号、平台、运行环境或新授权时才构成阻塞。报告：

- 受影响评分项和分值；
- 已完成的尝试及证据；
- 为什么无法自动继续；
- 需要谁提供什么；
- 解除后从哪一步恢复。

困难、耗时、问题多或会受益于建议不是阻塞理由。状态工具还应遵守当前环境对 BLOCKED 的重复确认要求。
