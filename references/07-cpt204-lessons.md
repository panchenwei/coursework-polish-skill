# CPT204 项目迭代经验

本文件记录方法来源，帮助其他 AI 理解为什么主 skill 强调证据链和最终验收。不得把这些项目专属数字自动套到别的作业。

## 1. 项目从哪里开始

项目最初不是“写报告”，而是：

- 阅读任务PDF、翻译版、Markdown要求和数据；
- 在没有JDK的环境中安装Java 17；
- 验证 early task；
- 分析候选数据和算法资料；
- 设计 Task A 的科研实验计划；
- 从空 `src`/`test` 正式实现；
- 再扩展 Task B、JavaFX、报告、PPT和提交包。

关键经验：课程项目必须先确定权威要求和输入，再做架构；不能从示例代码直接复制结构。

## 2. Task A 的迭代

从“能排序”扩展为：

- 三种手写排序共享同一比较规则；
- 完整排序后选择规定人数；
- 正确性、multiset、操作计数和三算法一致性验证；
- pilot、warm-up、formal raw timings；
- controlled input order；
- scaling；
- median/IQR、操作次数、递归深度；
- required table、boxplot、heatmap和其他证据。

一次重要失败是50次 warm-up 对很快的输入不足，pilot检测到前后半段漂移。解决方法不是删除异常值或降低门槛，而是增加到200次 warm-up并重新验证。

经验：pilot是正式实验的门禁；raw data、统计口径和失败记录比漂亮图更重要。

## 3. Task B 的迭代

最初需要明确：35名选中学生是重要节点，不是完整图的全部节点。最终流程是完整图上的BFS最短路、DFS分量遍历、四个官方case、无路径检查和分量分布。

DFS曾因“入栈即记录”而不像标准深度优先 preorder，后来改为显式栈帧、真正进入节点时记录，并增加 parent/depth/trace测试。

经验：结果看似正确不代表实现语义正确；测试要覆盖算法行为，不只覆盖最终集合。

## 4. 架构与代码润色

项目经历了两种相反风险：

- 类太多、职责过细，看起来难解释；
- 大类超过数百行，读取器、writer、figure builder和JavaFX页面职责混杂。

最终采用低风险拆分：保留公共入口和输出格式，用 package-private 协作者按真实职责拆分，所有正式输出哈希保持不变。

经验：不要按“类越少越像学生”或“类越多越OOP”判断。标准是职责、复用、依赖和作者能否解释。

## 5. JavaFX 的定位

JavaFX借鉴 early task 的伪代码/源码面板和动画过程，但连接真实排序器及保存的BFS/DFS trace，不复制第二套算法。排序动画使用演示样本，正式计时仍来自保存CSV。

经验：演示层可以增强理解，但必须明确“演示样本”和“正式证据”的边界。

## 6. 报告从“高级”变成“清楚”

报告早期内容丰富，却出现：

- required question第一句没有结论；
- 图表很多但没有说明证明什么；
- required table被heatmap替代；
- 复杂度只有结论没有推导；
- Appendix证据没有正文交叉引用；
- 图片/表格后出现大块留白；
- 新chapter不必要地另起一页；
- AI/EDI/反思过于模板化；
- Task C只说概念，没有真实类名。

多轮修改后形成“Direct answer → Evidence → Reason → Theory → Limitation → Implication”，并把完整材料放附录、正文保留关键论证。

经验：报告写得高级不等于老师能快速给分。最强写法是简单结论和深层证据并存。

## 7. 页数与版式

20页正文限制促使报告使用信息设计，而不是违规缩小字体。正文/附录分工、表图重排、删除重复和连续章节显著减少空白。

双列曾被当作节省空间的方案，但后来认识到“任务书没有禁止”不等于“明确允许”。任何非常规格式必须回到任务书或教师确认。

经验：格式合规必须由目标软件真实分页和页面图验证，LibreOffice/PDF/字数估计不能替代Word实际边界。

## 8. PPT与视频

PPT经历多轮提纲审查，最终原则是：

- official result table与解释图同时存在；
- 35个ID、四个case等强制输出直接展示；
- Task C/D不能被算法页挤没；
- UML聚焦接口与实现；
- 图的caption说明结论；
- JavaFX是补充；
- 讲稿按真实贡献分配并控制8分钟。

经验：PPT页数不是核心限制，清晰度和视频时长才是；高密度页可以拆开。

另一次明显返工来自把“满分目标”不断扩展成比任务书更苛刻的专业视频标准，评审循环一度超过实际制作进度。后来需要重新区分：官方评分门槛、合理质量提升和可选电影级制作，并恢复“先有完整成片，再做定向审查”。

## 9. 最终提交救险

最后阶段进行了：

- ZIP仅保留允许的Java文件；
- 主工作区、提交副本和ZIP逐文件比较；
- 干净解压后编译、运行和测试；
- 正式文件按教师命名；
- 从平台下载版本再比较；
- 检查Turnitin错误、Word临时文件和字段更新提示；
- 检查AI内部文件、缓存、数据和PNG未误入代码包。

经验：最终提交是独立工程阶段。项目本地能跑，不等于提交包完整、干净、可运行。

严格审查中还出现过两个重要校正：一是最初把内部工程规则误当成官方扣分点，后来按任务书重新计分；二是代码ZIP经教师确认只需Java源码，因此不能因未包含README、数据或脚本扣分。经验是：审查必须注明每个扣分依据，并允许高优先级新证据纠正旧结论。

报告的格式专修也证明了修改范围控制的重要性。用户要求只修字体、行距或单句时，必须用文本对比确认内容未被顺手改写；用户明确“其他不许碰”时，这本身就是本轮工作的硬边界。

AI声明最终采用如实披露：说明规划、检查、引用导航和文稿组织等真实用途，同时由源码、测试、raw CSV和原始文献承担事实证明。为了显得“人工”而缩小真实用途，会制造新的诚信风险。

## 10. 可推广总原则

1. 先读要求，后设计；
2. 先证明正确，后测性能；
3. 先保留raw evidence，后做图；
4. 先直接回答，后深入分析；
5. 正文完成论证，附录完成核验；
6. 修改代码要追踪所有下游制品；
7. 最终包必须在干净环境独立验证；
8. AI可以规划、检查和润色，但不能成为结果、PDF内容或作者经历的权威。
9. 官方要求和内部高标准分账管理；
10. 先交付可用成品，再做严格审计；
11. 局部请求严格锁定范围，范围外问题只报告；
12. 教师澄清按原问题和日期使用，不进行过度推论。
