# 代码迭代与润色流程

## 1. 先定义正确性

在实现前把每项功能写成可验证不变量：

- 输入是否合法；
- 输出的排序、范围、数量或结构；
- 输入输出元素集合是否一致；
- 路径首尾、相邻边和长度关系；
- 分区是否互不重叠且并集完整；
- 无结果时是正常状态还是异常；
- 相同输入是否需要确定性输出。

生产代码从输入计算结果。具体答案、精确计数和已知路径可以作为测试 oracle，但不能作为生产分支。

## 2. 分阶段实现

建议顺序：

1. 最小正确核心模型；
2. 输入解析和验证；
3. 核心算法；
4. 结果对象和正确性验证；
5. 集成入口；
6. 实验和统计；
7. 文件输出；
8. 图表与报告构建；
9. GUI/JavaFX/演示层；
10. 最终提交包装。

不要在核心算法未验证时先做漂亮 UI，也不要让 UI 成为唯一运行入口。

## 3. 结构原则

### 单一事实来源

这些规则通常只应有一个实现来源：

- 比较器；
- ID规范化；
- 路径或排序正确性；
- 统计公式；
- 图邻居顺序；
- 输出表头；
- 文件定位规则。

### 依赖方向

```text
models / domain
    ↑
algorithms and validation
    ↑
services / experiments / queries
    ↑
writers / figures / tables / UI / CLI
```

核心层不依赖 GUI、图表或报告。展示层读取结果对象或保存证据，不重写核心算法。

### 接口与抽象

只有满足至少一项时才引入接口或抽象类：

- 存在多个真实实现；
- 调用方需要可替换行为；
- 共享状态或不变量确实需要集中；
- 可以消除已测得的重复。

不要为了展示 OOP 使用单实现接口、深继承树、无意义工厂或依赖注入框架。

## 4. 学生可解释性

高质量学生代码不是“故意简单”或“故意不专业”，而是：

- 命名具体；
- 方法短而聚焦；
- 控制流可追踪；
- 注释只解释为什么；
- 错误信息有上下文；
- 没有隐藏魔法和过度泛化；
- 作者能逐类说明职责、数据流、复杂度和失败行为。

不要因为担心“像 AI”就删除合理测试、验证或结构。风险来自无法解释、与课程范围不符、模板化注释和无必要复杂度，而不是文件数量本身。

## 5. 测试层次

### 单元边界

- 空输入；单元素；正常输入；逆序或极端输入；
- 重复值和 tie-break；非法值；未知ID；
- 起点等于终点；无结果。

### 算法正确性

- 与独立 oracle 对比；
- 多实现输出一致；
- 输入输出 multiset 一致；
- 操作计数和定义一致；
- 递归/循环能终止；
- 路径和分区不变量。

### IO与格式

- BOM、CRLF、空行；
- 错误表头、缺字段、重复记录；
- UTF-8；
- 错误中包含文件和行号。

### 集成

- 上游结果真实传给下游；
- 不是从 console 文本反向解析；
- 全流程输出文件存在且内容一致；
- 总测试入口真实调用全部永久测试。

## 6. 低风险重构

在临近提交时：

- 先冻结正式输出哈希；
- 保持公开接口、文件格式和算法不变；
- 按真实职责拆分超大类；
- 用 package-private 协作者避免扩大公共 API；
- 每次拆分后重跑编译、测试和衍生物比对；
- 如果重构不能提升可解释性、消除重复或隔离变化，就不做。

## 7. 改代码后的连带检查

任何代码改动都可能影响：

- 测试 oracle；
- 实验结果；
- 图表和表格；
- 报告中的类名、伪代码、复杂度与代码章节；
- UML；
- PPT截图；
- 提交包；
- 运行说明。

建立 affected-artifacts 列表，不能只修主工作区而遗漏最终副本。
